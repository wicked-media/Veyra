# Data model

## 1. Principles

- **Tenant scope:** every firm-owned table carries `organisation_id`; queries must filter by the
  actor's firm.
- **Referential integrity:** foreign keys enforce ownership; deletes are restricted or cascaded
  deliberately.
- **Real migrations:** schema changes are generated by Drizzle Kit and reviewed; no runtime schema
  sync.
- **Auditability:** consequential mutations write audit events in the same transaction.
- **Retention-aware:** soft deletion/archival where the law requires records to remain available.
- **No speculative explosion:** only tables needed by implemented or immediately next modules exist.

## 2. Implemented tables (16)

### Tenancy
| Table | Purpose | Key constraints |
| --- | --- | --- |
| `organisations` | Tenant/firm, timezone, financial year, matter prefix | unique `slug`; `archived_at` |
| `offices` | Firm offices/branches | unique `(organisation_id, name)` |
| `departments` | Teams/practice groups | unique `(organisation_id, name)` |

### Identity and access
| Table | Purpose | Key constraints |
| --- | --- | --- |
| `users` | Global person identity and scrypt password hash | case-insensitive unique email |
| `memberships` | User's role/status/title in a firm | unique `(organisation_id, user_id)` |
| `sessions` | Server-side session token hash and context | unique token hash; expiry index |

A user can belong to multiple firms. Access is always through an active membership; switching firms
updates the session's organisation after checking that membership.

### Clients
| Table | Purpose | Key constraints |
| --- | --- | --- |
| `clients` | Individual or organisation client, risk rating, source, notes | indexes on firm/status/name |
| `client_contacts` | People at a client | client/firm indexes |
| `client_addresses` | Physical/postal addresses | client index |

### Matters and work
| Table | Purpose | Key constraints |
| --- | --- | --- |
| `matters` | Matter record, reference, practice area, status, responsible solicitor, restriction | unique `(organisation_id, matter_number)` |
| `matter_members` | Explicit matter team and matter role (`lead`, `member`, `viewer`) | unique `(matter_id, user_id)` |
| `matter_walls` | Ethical wall deny-list with reason | unique `(matter_id, user_id)` |
| `matter_parties` | Client, opposing, counsel, third party, related | matter index |
| `tasks` | Firm-level or matter-level tasks | indexes on firm/status/matter/assignee/due |
| `matter_sequences` | Per-firm/per-year next matter number | PK `(organisation_id, year)` |

### Audit
| Table | Purpose | Key constraints |
| --- | --- | --- |
| `audit_events` | Append-only evidence of actions | bigserial id; indexes on firm/time, entity, matter |

`audit_events.matter_id` is intentionally not a foreign key: audit history must survive matter
retention changes. `actor_user_id` is `SET NULL` so history remains after a user is removed, with
metadata preserving context.

## 3. Relationships

```
organisations 1─* offices
organisations 1─* departments
organisations 1─* memberships *─1 users
organisations 1─* clients 1─* client_contacts
                        1─* client_addresses
                        1─* matters 1─* matter_members *─1 users
                                    1─* matter_walls
                                    1─* matter_parties
                                    1─* tasks
organisations 1─* matter_sequences
organisations 1─* audit_events
```

A task may have no matter (firm-level) but still belongs to a firm. Matter parties are records, not
global contacts; a future client/contact linking model must preserve existing party history.

## 4. Matter numbering

`matter_sequences` holds `(organisation_id, year, last_value)`. Inside the matter transaction:

```sql
INSERT INTO matter_sequences (organisation_id, year, last_value)
VALUES (..., 1)
ON CONFLICT (organisation_id, year)
DO UPDATE SET last_value = matter_sequences.last_value + 1
RETURNING last_value;
```

The row update locks the sequence, so concurrent creates cannot duplicate a number. The formatted
reference is `PREFIX-YYYY-0000` using the firm's time zone for the year. The unique index is the
final backstop. Changing a prefix affects new matters only.

## 5. Authorisation queries

Matter visibility is centralised in `packages/core/src/access.ts`:

- firm scope on every query,
- `NOT EXISTS` wall for the actor,
- unrestricted **or** `EXISTS` explicit team membership.

This condition is reused by matter lists, workspace access, task visibility, dashboard activity,
audit filtering and insights. A future document table must join through the same condition, not a
parallel permission system.

## 6. Audit immutability

Migration `0001_audit_append_only.sql` installs a PL/pgSQL function and triggers:

- `BEFORE UPDATE OR DELETE` on each row,
- `BEFORE TRUNCATE` on the statement.

Any attempt raises an exception. The trigger is part of the schema and applies to the application
role; a superuser could disable it, so database role separation is still required in production.
Tests verify updates, deletes and truncation are rejected while inserts continue to work.

## 7. Migrations

- `packages/database/migrations/0000_pale_moonstone.sql` creates the schema.
- `0001_audit_append_only.sql` adds audit triggers. It uses Drizzle's
  `--> statement-breakpoint` markers because the PGlite migrator executes prepared statements.
- `meta/_journal.json` tracks applied migrations.
- Generate with `pnpm db:generate`; never edit generated migrations after they ship. Add new ones.

Production should apply migrations in a dedicated job before deploying application instances, with
backups and a rollback plan. Stage 1 applies them on startup for local convenience.

## 8. Indexes

Designed for current access patterns:

- matters: firm + status, firm + client, responsible solicitor, unique firm + number.
- tasks: firm + status, matter, assignee, firm + due date.
- audit: firm + created time, entity, matter.
- clients: firm, firm + status, firm + name.
- memberships: firm + role, user.
- sessions: token hash, user, expiry (worker cleanup).

Add indexes only with a measured query. Review write amplification before adding broad indexes.

## 9. Retention and deletion (design)

Stage 1 does not implement retention automation. Intended design:

- Firms are archived, not hard-deleted, while legal retention obligations apply.
- Clients/matters are archived; deletion requires an authorised, audited retention workflow.
- Documents will support legal hold that blocks deletion.
- Audit records are retained independently and never cascade with matter deletion.
- Personal information deletion requests must be assessed against professional and statutory
  retention duties; the outcome is recorded.
- Data export must include client, matter, document metadata, audit and a manifest.

## 10. Future domains

To be added incrementally with requirements: documents and versions, document permissions and
holds, correspondence, calendar/deadlines, time entries, expenses, invoices/payments, workflow
